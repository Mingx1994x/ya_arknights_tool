- 「手動模擬排程」（`ManualPlanTab.vue`）改採「逐階段即時計算」流程：拆分「起始階段」（`startStage`）與目前編輯階段（`currentStage`）兩個狀態，完成一階段（選好 critical 幹員與陪練幹員）後點「前往下一階段」才把該階段鎖定成唯讀摘要卡片並前進；下一階段的所需工作量改用「上一階段實際鎖定的 `triggersNextHalving`」（依使用者真實填的 critical 幹員陪同時長是否 `≥5hr` 判斷），取代原本 `getRequiredWorkUnderDefaultStrategy` 寫死一定觸發減半的假設（已移除該函式），修正了前一則條目提到的「手動模擬排程仍是舊版邏輯」問題；改動起始階段或幹員職業會清空已鎖定階段、整個重新開始。已完成階段目前尚未支援回頭編輯，見 [FEATURES.md](./FEATURES.md) 待辦。

### Changed
- 統一 `app/utils/mastery.ts` 的階段陪同策略函式命名，對齊 UI 端已在用的 `'general' | 'base' | 'critical' | 'final'` 四種階段變體（`StageForm.vue`／`StageCard.vue`／`ManualPlanTab.vue`）：`planCriticalCompanionStage` 改名 `generalCompanionStage`；新增 `baseCompanionStage`（單一陪練幹員直接反推，取代 `suggestStagePlans` 與 `ManualPlanTab.vue` 內散落的 `calcDurationForWork` 呼叫）與 `criticalCompanionStage`（critical 幹員獨自補滿所需工時直接反推，回傳值含 `triggersNextHalving`，取代 `ManualPlanTab.vue` 的內嵌門檻比較邏輯）；`final` variant 計算邏輯與 `base` 相同，純屬 UI 結構鎖定，不需要獨立函式。`baseCompanionStage`／`criticalCompanionStage` 兩者只處理單一幹員，回傳欄位統一改名 `operatorDurationHours`（原本分別是 `otherOperatorDurationHours`／`criticalDurationHours`，沒有歧義所以不需要「other／critical」前綴）；`suggestStagePlans`（`MasteryStageAutoPlan`）同步套用，因為該策略下 critical 幹員的陪同時長已由 `CRITICAL_DEFAULT_DURATION_HOURS` 固定，回傳的唯一時長欄位不會混淆，也改名 `operatorDurationHours`（原 `otherOperatorDurationHours`）；`generalCompanionStage`（`CriticalCompanionPlan`）因為同時回傳 critical 與陪練幹員兩者，仍保留 `otherOperatorDurationHours` 以區分。同步新增 `app/types/mastery.ts` 的 `BaseCompanionPlan`／`CriticalOnlyCompanionPlan` 型別，並刪除 `suggestStagePlans` 上方已停用的舊版「整階段單一候選幹員」模型註解區塊。純命名/結構調整，計算邏輯與行為不變。
- **`app/utils/mastery.ts` 內部計算單位改為「分鐘」，取代「小時的小數」**（`docs/domain/arknights_tools_init.md` 第 2 節）：`TBASE_HOURS`→`TBASE_MINUTES`（480/960/1440）、`HALVING_THRESHOLD_HOURS`→`HALVING_THRESHOLD_MINUTES`（300）、`CRITICAL_DEFAULT_DURATION_HOURS`→`CRITICAL_DEFAULT_DURATION_MINUTES`（305，改用分鐘後是精確整數，不再是 `5 + 5/60` 這種無限循環小數）；`calcPhaseWork`／`calcDurationForWork` 參數改為分鐘；`baseCompanionStage`／`criticalCompanionStage`／`generalCompanionStage`／`suggestStagePlans` 回傳欄位改名 `operatorDurationMinutes`／`otherOperatorDurationMinutes`／`maxCriticalDurationMinutes`；`formatHoursAsHm` 改名 `formatMinutesAsHm`，直接對分鐘數 `Math.round` 後取商餘數，不再需要先乘以 60。`ManualPlanTab.vue` 的 `rawCriticalDurationMinutes`（原 `rawCriticalDurationHours`）改用 `criticalHours * 60 + criticalMinutes`（整數相加）取代原本 `criticalHours + criticalMinutes / 60`（除以 60 的無限循環小數）；`createDefaultPlanState()` 的預設 `criticalHours`／`criticalMinutes` 改用整數除法 `Math.floor(CRITICAL_DEFAULT_DURATION_MINUTES / 60)`／`% 60` 反推，不再有小數。`AutoPlanTab.vue`／`StageCard.vue`／`StageForm.vue` 對應 props（`requiredWorkHours`等）同步改名 `...Minutes`。純屬內部單位的工程精度調整，**不改變任何公式或數值結果**——使用者輸入介面（「時」／「分」兩個獨立輸入框）維持不變，只是內部計算鏈不再需要「小時的小數」，避免浮點數誤差沿計算鏈累積。
- `ManualPlanTab.vue`（手動模擬排程）的「當前階段是否已套用跨階段減半」改為以當前階段為主的直接狀態：`isCurrentStageHalved` 從 computed（每次讀取都要反查 `lockedStages[currentStage - 1]?.triggersNextHalving`，還要額外處理起始階段沒有上一階段的特例）改成 `ref<boolean>`，在 `advanceToNextStage()` 推進階段的當下直接把剛完成階段的 `triggersNextHalving` 寫入、`resetProgress()` 重置回 `false`，讀取端不用再反查歷史紀錄（變數名稱不變，只換內部實作方式）。純架構調整，行為不變；`AutoPlanTab.vue` 原本就是宣告式的當前階段判斷（`group.phase > startStage`），不受影響。`app/utils/mastery.ts` 的 `getRequiredWork()` 第二個參數同步從 `previousPhaseTriggeredHalving` 改名為 `isHalved`（純改名＋JSDoc 更新，邏輯不變），呼應「函式只需要知道當下這個階段是否已減半，不需要知道是怎麼推導出來的」。
- **修正專精工作量公式：基地 5% 加成改為與陪同幹員效率加成相加，而非分開相乘**（`app/utils/mastery.ts` 的 `getRequiredWorkBase`／`calcPhaseWork`／`calcDurationForWork`，`docs/domain/arknights_tools_init.md` 第 3、5、7 節）。原公式 `RequiredWorkBase(N) = Tbase(N) / 1.05` 搭配 `phase.work = duration × (1 + efficiencyBonus/100)`，等同把 5% 跟陪同加成用相乘方式合併；比對 Google 試算表「方舟專精計時器」的對照組公式，以及使用者實際操作專精一（水陳 95% 加成 → 切換艾麗妮 30% 加成）時遊戲介面顯示的倒數時間，發現相乘模型穩定偏差 4～5.5 分鐘，改成相加模型（`RequiredWorkBase(N) = Tbase(N)`，`phase.work = duration × (1 + 0.05 + efficiencyBonus/100)`）後，三個檢查點誤差都在 1 分半內。
